## 开席与更新

1. 从 39 的站点配置核对默认镜像、部署目录及 Connector。核对镜像标签 `io.cellgent.dsh-dingtalk.revision` 和构建产物。通用镜像仅继承已验证的插件代码；工作区、个人配对和 Connector 凭据保存在各自的持久化位置。企业 profile 的 `robotConnection.queryTools` 使用席位已获准的 14 个只读问数工具，清单见[工作区工具策略](../WORKSPACE-TOOL-POLICY.md)。
2. 发布新模板时同时切换 `/etc/cellgent/dingtalk-seats.json` 的 `image`、`deploy`。先保存旧配置，在同目录写入并校验新文件，保留原所有者和权限，再原子替换。39 的开席命令在选中站点默认镜像时才会自动绑定 Connector。日常开席沿用默认参数，由开席程序核对企业下唯一的员工身份，生成该员工专属的只读 socket 挂载。身份缺失或重复时先核对身份记录。
3. 已有席位从台账取完整用户 ID 和原 tier，核对容器标签、镜像和工作区挂载后逐席更新。下例在已加载站点管理环境后运行，`USER_ID`、`TIER`、`OPERATOR` 均由操作者填写。先看预演选中的镜像、部署目录和该员工的 socket，再执行同一席位的更新。每个席位通过下节检查后再处理下一个。

```sh
cellgent-admin grant "${USER_ID:?}" --tier "${TIER:?}" --recreate --by "${OPERATOR:?}" --dry-run
cellgent-admin grant "${USER_ID:?}" --tier "${TIER:?}" --recreate --by "${OPERATOR:?}"
```

4. 员工在「设置 → 钉钉连接」分别完成本人的 DWS 登录和企业机器人的设备配对。机器人入群后，网关配置 `allowedGroups: []`、`groupMentionSenders: "all"`，按带有机器人 @ 的群消息中的企业和**发送人**匹配在线绑定。新席位完成本人配对即可使用。群内回复对该群成员可见。网关配置通过宿主机文件挂载，在原子替换文件后单独重启 `dsh-dingtalk-gateway-1`，核对容器实际读到的新配置及原在线席位重连。

## 按故障范围回滚

**仅撤回全员群 @。** 核对当前网关镜像和 `group-all-receipt.json`，确认现行策略为 `"all"`。从 `pre-group-all.gateway.private` 取出上一版 `groupMentionSenders`，只将这个字段写回当前网关配置，保留现有企业配置和其他字段。提交前比较更新前后的 JSON，差异应恰好为这一项。按原所有者和权限在同目录原子替换，再执行 `docker restart dsh-dingtalk-gateway-1`。比较宿主机文件与容器中 `/etc/dsh-dingtalk/gateway.json` 的摘要，确认启动成功及原在线席位重连。本操作保留当前设备绑定。

**撤回默认模板和推广席位。** 在站点维护窗口记录当前 `image`、`deploy`，核对其与此次回执一致；确认 `site.before` 指向的旧镜像 ID 和部署目录均可用。先从该备份将 `image`、`deploy` 一起还原到现行站点配置，再按上面的逐席命令重建需要回退的推广席位。只改默认值不会改变运行中的席位；直接给命令传旧镜像可能跳过 Connector 自动绑定。每次比对更新前后的 tier、工作区、席位 socket、员工身份与连接状态。遇到不一致，停止下一席并保留现场。若只需撤回新开席位的默认值，到还原站点配置为止。

**单独回退先行席位。** 两个先行席位曾使用不同的镜像及部署入口。取对应先行发布记录中的容器变更前快照、管理入口及配置，核对其旧镜像 ID、原部署目录及 socket。使用该席位原管理入口预演和重建；不能将两席套用通用模板。回退以工作区、既有授权和健康检查通过为准。插件或群策略回退均不需要恢复旧绑定库；仅发生状态数据损坏时使用 [Connector 备份与恢复流程](../../connector/docs/BACKUP-RESTORE.md)。
