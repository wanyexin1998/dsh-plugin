# 第二阶段：本人三个入口共用授权

开发分支：`feat/dingtalk-phase2-shared-identity`。本阶段只面向一位已绑定的 owner，在同一本机 DSH Profile 内，让 Web、机器人私聊和获准内部群聊复用同一份 DWS 授权。多人各自授权、跨企业转换和数字员工不在本阶段范围内。

## 实现

1. Web 继续使用原有官方 OAuth 流程，保存精确的 `corpId:userId` Profile。机器人应用凭据只负责接收和回复消息，不替代个人 DWS 授权。
2. Stream 保留 `senderCorpId`、`senderStaffId` 和 `chatbotCorpId`。以消息的 `senderCorpId + senderStaffId` 作为调用者身份；昵称、会话 ID、模型参数都不参与身份认定。缺少发送者企业字段时拒绝个人数据调用，目前不猜测 `chatbotCorpId` 的替代语义。
3. 官方 owner 绑定和群准入仍生效。在此之上，仅 owner 可以发起工具调用。Agent 作用域覆盖同名 `dingtalk_call`，从受信消息上下文取身份，每次与当前 Web 绑定精确比较，匹配才进入同一个 managed reader 和执行队列。
4. 一个 Agent 的身份在首次有效消息后固定，后续企业或用户变化拒绝该任务。身份不放进模型可填写的 JSON，也不存入第二套账号库。Web、私聊和群聊仍各自保留会话；工作区沿用原有配置，不因身份统一而合并。
5. 高影响操作沿用 Host 原生 approval 和官方 IM 确认。`never` 策略仍拒绝，不绕过。等待审批时捕获实际 reader 和授权版本；Web 断开或重新授权后，旧审批不能在新账号上执行。

没有复制 Token、切换进程级默认 Profile、第二次扫码或新增身份映射数据库。仍使用原有 CLI 的刷新与凭据校验，未新增远程身份请求。

服务重启后，如果绑定会话已由 Web 加载，机器人自动建立新的 IM 会话，保留旧会话历史，不接管或修改 Web Agent。新会话不继承旧会话上下文。会话创建等调度失败时发送简短提示，避免仅记录后台错误而让用户无回复。

## 使用

同一本机 Profile 中先完成 Web 钉钉连接，再为机器人配置应用凭据、Stream 模式与可见范围，沿用官方 `/bind` 完成 owner 绑定。私聊由本人发送请求；内部群需先按官方配置允许该群，再由本人 @ 机器人。群内回复对群成员可见，应选择适合在群内展示的数据。

若 Web 未连接或已断开，IM 返回需要连接；若两个入口不是同一企业的同一用户，返回身份不匹配。应在 Web 连接到本人当前企业账号，不通过默认账号兜底。更换了 owner 或企业且复用了旧 Agent 时，应新建会话。

本阶段 IM 开放 `dingtalk_call`、技能读取和用户询问，继续限制任意本机执行、子 Agent 和文件回传工具。Web 的权限与前端组件不变，旧 `tools.enabled` 也不会开启另一套 DWS 执行器。

## 本地验收

- 消息身份字段透传与缺失处理；跨企业同 userId、跨用户及模型伪造参数不借用 Web 授权。
- 同一个 managed connection 的 Web 与 IM 调用访问同一合成用户；断开、重启、重新授权后的行为。
- 等待审批时断开并换账号，不执行旧操作；被拒绝的审批不写入。
- 真实 DSH ToolRuntime 验证作用域覆盖：IM 使用自己的入口，其他工具被限制，Web 仍用原入口。
- `pnpm run ci` 在本机运行；`DSH_TEST_RUNTIME` 指向测试运行库后运行 `node scripts/verify-boundary.mjs`。不配置 GitHub Actions。

真实验收必须另行记录：发布机器人后检查私聊与内部群的实际企业字段；本人三个入口分别查询同一信息；非 owner 群消息不触发数据查询；Web 断开后 IM 不再使用旧授权。模拟端点测试不能替代这些验收。
