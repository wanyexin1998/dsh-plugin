# 手写 SQL 的流畅度：第一性原理分析与 dsh-data-ide 优化/新增清单

> 性质：**设计分析，不改代码**。本文只谈「人坐在 IDE 前手写 SQL」这一件事；agent/MCP 工具面的方案见 `PLAN-borrow-from-ide-workbench.md`。
> 证据：三份只读调研（当前实现盘点 / DataGrip 逆向材料的边界 / 外部工具对照）+ 代码与文档行号。
> 结论口径：凡「当前行为」以代码为准（工作区含 67 个未提交改动）；凡「外部工具行为」以官方文档为准，不拿 DataGrip 常识冒充逆向结论。

---

## 0. 一页结论

### 0.1 一句话

**手写 SQL 的瓶颈不是打字，而是一次「发现型闭环」的周期：意图 → 侦察（库表是什么）→ 起草 → 自检 → 执行 → 检视 → 修改 → 收割。**
流畅 = 这个闭环转得快、每一圈的信息不丢、每一步都少看别处；优化顺序应是 **减少往返/等待 > 减少记忆 > 减少击键 > 美化**。

## 1. 第一性原理：手写 SQL 到底是什么

### 1.1 一次查询的 8 个步骤

| 步 | 人在做什么 | 现在 IDE 给的支持 | 典型摩擦 |
|---|---|---|---|
| 1 意图 | 明确要回答什么问题、用什么口径 | 无（聊天/需求在外部） | 口径靠记忆 |
| 2 侦察 | 找表、看列、看样例值、确认库 | 对象树 + 补全 + 表结构 | 补全在 `FROM`/`WHERE` 失效；没有样例值 |
| 3 起草 | 写 SELECT/JOIN/WHERE/GROUP BY | 高亮 + 12 模板 + 补全 | 样板代码多；`*` 要手敲列；JOIN 条件靠记忆 |
| 4 自检 | 语法对不对、列在不在、会不会全表扫 | **几乎没有** | 只能跑一次才知道 |
| 5 执行 | 跑，等 | 执行/取消/分页 | 跑整段、等 COUNT、脚本不可取消 |
| 6 检视 | 看数、看形状、找异常、算聚合 | 网格 + 排序/筛选/聚合/值查看器 | 不能查找/隐藏列；宽表难读 |
| 7 修改 | 改条件、改聚合、改粒度 | 重新编辑 + 重跑 | 状态不连续；旧排序/筛选粘着；选区 bug |
| 8 收割 | 复制结果、导出、保存、交给 agent | 复制 TSV/导出/agent 投递 | 无 INSERT/JSON；无「结果→SQL」 |

**关键观察**：第 4 步（自检）几乎空白，第 7 步（修改）的摩擦最高，第 8 步（收割）需要人工搬运。而第 2–3 步的很多动作可以靠「元数据 + 纯前端」解决——这正是当前最大的性价比区。

### 1.2 与普通编程的 5 个不同（决定设计取舍）

1. **规格是数据本身**：写之前不知道数据长什么样，执行就是「编译 + 运行 + 观察」。所以 IDE 必须让**执行便宜**，并允许「先看一小部分」。
2. **没有单测**：正确性靠人眼看结果、对比口径、聚合验证。所以结果区不是输出，而是**验证界面**。
3. **执行有成本**：一条坏 SQL 可能扫全表、跑几分钟。所以要有**执行前验证**（lint/EXPLAIN/行数预览）和**随时可取消**。
4. **标识符长且来自元数据**：表名列名是业务词（`dwd_trade_order_all`、`order_amt`），回忆成本远大于敲键盘成本。所以**补全和对象导航的价值 > 输入法/多光标**。
5. **SQL 是声明式 + 方言化**：同一意图有大量等价写法，方言细节多。所以**模板/生成/格式化**比「智能重写」更实用。

### 1.3 成本模型

单次迭代时间 ≈
**Σ 思考** + **Σ 击键** + **Σ 等待** + **Σ 看别处（上下文切换）** + **Σ 返工（跑错/写错）** + **Σ 搬运（复制到别处）**

每类成本对应的机制：

| 成本 | 主要由什么降低 | 本文对应条目 |
|---|---|---|
| 记忆 | schema 补全、对象搜索、hover、历史、收藏、表统计 | §4、§5.1 |
| 表达 | 模板、`*` 展开、列清单生成、JOIN 生成、格式化、多光标 | §5.2 |
| 验证 | lint、EXPLAIN、LIMIT 预览、行数、结果聚合/对比、错误行号 | §5.3 |
| 等待 | 执行光标语句、直跑模式、不默认 COUNT、取消、缓存 | §3.1、§3.2 |
| 看别处 | 结果就地/绑定、错误回编辑器、命令面板、快捷键 | §4、§6 |
| 返工 | 执行前验证、错误可行动、旧结果/历史不丢 | §3、§5.3 |
| 搬运 | 结果→SQL、导出、复制、agent 交接 | §5.4 |

### 1.4 七条原则（从第一性原理推出）

1. **状态留在 IDE**：当前连接、上次 SQL、历史、排序/筛选、光标位置都不该由人重复表达或重新找回。
2. **验证左移**：能在写的时候/跑之前发现的，绝不留给「跑一次」。
3. **每次执行都要值得**：默认执行「光标语句」而不是整段；能先看 N 行就不跑全量；能看计划就不盲跑。
4. **输出要变成输入**：结果能变 SQL、筛选能变 WHERE、错误能变修复、历史能变模板。
5. **渐进精度**：先 LIMIT/EXPLAIN/样例值，再全量；先高置信度 lint，再考虑语义分析。
6. **非破坏性**：格式化要预览/可撤销；生成要进新 tab；AI 结果要 diff；覆盖正在写的内容必须先确认。
7. **可发现**：任何动作至少两处可达（菜单/快捷键/命令面板）；菜单里的快捷键提示必须真实可用。

### 1.5 优化顺序

**减少往返/等待 > 减少记忆 > 减少击键 > 美化。**
原因：一次多等的 COUNT 或一次跑错的全表扫描，抵得上几十次击键优化；而「漂亮」只在其他都成立时才有价值。

## 3. 三处结构性断裂（本文的重点判断）

### 3.1 断裂一：执行语义与手写节奏不匹配

**现状（证据）**
- `Ctrl+Enter`/工具栏：有选区跑选区，否则跑**整个 console**；多语句 → 逐条跑全脚本。
- Bug：选区只含 1 条语句时，走「单语句分支」却把 `query`（整段文本）传给 `executeQuery`，服务端再用裸 `sql.split(';')[0]` 取第一条 → **选第 2 条会跑第 1 条**（`SqlWorkbenchPanel.tsx:885-896`；`execute/core.ts:238-242,342`）。
- 单语句路径的 `firstStatement()` 不识别字符串/注释里的 `;`（`WHERE a = 'x;y'` 会被截断）。
- 脚本执行不可取消；执行中再按 `Ctrl+Enter` 无守卫，会并发第二个请求并互相覆盖。
- 无「重跑上次」「重跑当前结果对应语句」。

**第一性原理**：手写时最常见的动作是「改一句 → 跑一句」，而不是「跑整个文件」。执行单位必须是**语句**，且执行目标必须由光标显式可见。

**方案**
1. `Ctrl+Enter` = 执行光标所在语句（无语句边界时=全文）；`Ctrl+Shift+Enter` = 执行全部；**选区始终最高优先**，且单条选区也必须真跑选区。
2. 用 `splitStatements()` 的 `start` + 分号扫描计算每条语句的 `[start,end)`，按光标 offset 命中；空行/注释/括号边界要有测试。
3. 修 `firstStatement()`：改用 `splitStatements(sql)[0].text`（与脚本路径同一套扫描器）。
4. 执行中：键盘重入守卫（排队或忽略），按钮已禁用；取消用 Abort + 请求代次，旧响应不得覆盖「已取消」。
5. 脚本执行补 statementId 与取消通道；失败语句可单独重跑（结果 tab 上「重跑这条」）。
6. 工具栏显示「将执行：第 2 条 · 3 行」；有选区时显示「将执行选区」。

**验收**：光标在第 2 条语句按 `Ctrl+Enter`，只执行第 2 条；选第 2 条整句按 `Ctrl+Enter`，执行第 2 条；连按两次只发一个请求；脚本执行中可取消。

### 3.2 断裂二：手写查询被「分页浏览」语义绑死

**现状（证据）**
- 所有 SELECT 都被包成 `SELECT * FROM (用户 SQL) AS t [WHERE 筛选] [ORDER BY] LIMIT n OFFSET m`，并并行发 `SELECT COUNT(*) FROM (用户 SQL) AS t`；COUNT 1.2s 超时后 `total=null`（`execute/core.ts:180-196,361-376`）。
- 元数据语句（SHOW/DESC/EXPLAIN/SHOW CREATE）进包裹必语法错；面板只有把请求标成 `raw` 才能执行（`SqlWorkbenchPanel.tsx:702`；`docs/03-UIUX-SPEC.md:94-98`）。
- 错误行号来自包裹后的 SQL（用户 SQL 前面多了一行 `SELECT * FROM (`）→ 行号偏移。
- 脚本每语句都跑一次包裹 + COUNT → 10 条语句最坏 = 10×COUNT 等待。
- DataGrip 的事实：**console 手写 SQL 不分页，分页只发生在数据编辑器**（`docs/reference/RUNTIME-FINDINGS.md:218`）。

**第一性原理**：写 SQL 时的动作是「验证这条 SQL 会返回什么」，不是「浏览一个已经确定的结果集」。前者要求**原样执行、快速首屏、错误对得上行**；后者才需要 COUNT/翻页/排序/筛选。把两者合成一个动作，等于让每次手写都付浏览的代价。

**方案：双模式**
| 模式 | 触发 | 行为 | 结果区 |
|---|---|---|---|
| **执行（写）** 默认 | `Ctrl+Enter` / 执行按钮 | 元数据语句（SHOW/DESC/EXPLAIN/SHOW CREATE）原样执行；SELECT 只取前 N 行（N=200/500，可配），**不 COUNT、不加排序/筛选**；错误行号与用户 SQL 一致 | 「前 200 行 · 行数未知」+「统计总数」按钮 |
| **浏览** | 点「统计总数/翻页/排序/筛选」或结果区操作时 | 切到现有分页包裹模式（COUNT + ORDER BY + WHERE + OFFSET） | 现有分页条与总数 |

实现要点：
- 服务端 `ExecuteRequest` 增加 `mode: 'direct' | 'paged'`（默认 direct）；direct 分支对 SELECT 只加外层 `LIMIT`，对疑似结果集语句用 `raw`；paged 保持现状（AC-2/AC-3 不变）。
- `LIMIT` 注入要安全：用户 SQL 已含顶层 LIMIT 时直接原样执行（可能返回更多，也可能更少）；无法判断时包一层 `LIMIT`（错误行号做偏移校正）。
- 错误行号：direct 无需校正；paged 在错误体里回传 `lineOffset` 或直接换算成人话「你的 SQL 第 N 行」。
- 结果区提示「已执行原样，未统计总数」；按钮一键切浏览模式并保留数据。

**收益**：写查询的首屏不再等 COUNT；SHOW/DESC/EXPLAIN 一键可用；错误行号对得上；脚本执行更快。
**风险**：AC-2/AC-3 的验收对象是浏览模式，需明确写进规格；`LIMIT` 注入的边界要有测试；direct 模式下大结果的安全性（只读前 N 行 + 驱动侧限制）。

### 3.3 断裂三：状态不留在 IDE

**现状**：console 文档是纯客户端状态，刷新全丢（B4）；无查询历史（B5）；无收藏；`sort/filters` 粘在 console 上（换 SQL 仍带旧条件）；对象树「打开数据」覆盖当前 SQL。

**第一性原理**：SQL 手写是**跨会话**的：昨天跑对的那条、上周的口径、正在改的草稿，都是资产。IDE 不替人记住，人就要自己记。

**方案**
1. **B4 console 持久化**：按连接/工作区存 SQL 文本、活动 tab、光标、页大小、滚动位置；不存结果集；用宿主 storage（复用 B3 layout 的通道）。
2. **B5 查询历史**：每次执行记录 `{connId, sql, at, durationMs, rowCount, ok, errorCode}`；可搜索/按连接过滤/按表过滤；`Ctrl+↑` 或 `Ctrl+Shift+H` 调出；双击插入/替换；可钉住。
3. **收藏/片段**：把常用 SQL 存成命名片段，进入补全候选（参考 Redash 的 snippet 进补全）。
4. **状态卫生**：换 SQL 重跑时提示/重置旧 `sort/filters`；对象树「打开数据」默认**新 tab**（或先确认），不覆盖正在写的内容。

**验收**：刷新后 100% 恢复工作现场；「昨天跑过的一条」30 秒内找到并回填；换 SQL 不会莫名被旧筛选过滤。

## 6. 不做什么 / 慎做

| 项 | 原因 |
|---|---|
| 全量 PSI / 语义分析引擎（类型推断、作用域、跨语句 resolve） | PRD N4 明确不做；成本是「重客户端」级别。轻量 lint 只做高置信度规则即可 |
| 图表 / 结果对比 / 编辑回写（N1/N5） | 超出「轻量 SQL 工作台」定位；`AGENTS.md:123` 已排除 |
| 强制格式化 / 保存即格式化 | 探索期会打断节奏；只在显式触发时格式化 |
| 每次执行都弹参数绑定窗 | DBeaver 的既有教训；参数条常驻 + 记住上次值 |
| 重模板系统（多类型/多变量/多上下文） | 学习成本 > 收益；12 个 live template 已经够用，扩展按需 |
| 为省一次点击引入模态框 | 打断成本 > 点击成本；优先内联/就地 |
| 让 agent 自动修改 SQL | 手写场景信任成本高；必须 diff + 接受 |
| 过早把 AI 当主入口 | 手写场景的主导动作是「编辑 + 验证」；补全/格式化/lint 是确定性的、不依赖模型质量，先做这些收益更稳；AI 适合当「生成草稿 / 解释 / 修复候选」的补丁层（BigQuery 的 Preview→Accept 是先例） |
| 大而全的快捷键 | 冲突与记忆成本高；命令面板 + 10 个核心键 |
