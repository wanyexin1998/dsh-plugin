# 开工指令与变更流程

## 1. 可直接转发给开发团队

请按 **BOOP v1.2-FROZEN-R1** 开工。先校验交付包，再阅读第01、02、03册和Taskboard复用附册；前端/视觉阅读第04、05册。`baseline/`是不可覆写的设计快照，交接附录是执行入口。

第一批建立E00-01、E00-02、E00-03、E05-00、E04-00；D01-01可以并行。请在隔离DSH_HOME和合成样本上验证，先获得rc.2装配、自定义消息来源、启动恢复门禁、SQLite和实际Qwen接入证据，再实现个人可用闭环。模型配置由安全通道提供，缺参数时推进其他独立项并明确BLOCKED。

所有任务、PR、审查、失败证据和变更申请记录在团队实际GitHub仓库。`handoff/issues/`是可复制正文，不是已经创建的Issue。不要重复分配已有工作：负责人导入时先核对现有Issue/分支再关联本包ID。

不得重写原生Loop、整包接入Taskboard服务、建立第二任务库、冒充用户消息或绕过审批。历史初始化不恢复旧任务，Host重启业务必须谨慎恢复。保持单主聊天、会话内消息、原生UI和已确认蓝鲸，不做新产品方向。

每个PR必须附明确范围、实际commit、对应Gate/AT/TB/FE、真实测试结果、数据和权限影响、回滚及未完成项。没有运行的标NOT_RUN，缺条件标BLOCKED，文档QA不能代替产品QA。先交个人使用版，再交两个IM渠道，最后做公开发布审查。

## 2. 第一轮团队回执

| 回执 | 要求 |
|---|---|
| 任务登记 | 本包ID → 实际Issue/负责人/分支；已有任务只关联不重复建 |
| 版本 | DSH/tag/commit、Node/Electron/OS、其他插件与测试DSH_HOME |
| 模型 | 可用路由、鉴权引用、实际上下文/输出限制和待补参数；不回传密钥 |
| Gate | G01/G02/G03/G04/G08/TB02各自状态、证据与阻断 |
| 后续计划 | 根据PoC结果给出估算与并行拆分；不凭文档猜固定人天 |

## 3. 分支与PR约定

建议分支`feat/<工作项ID>-<短名>`，例如`feat/e00-02-proxy-gate`。名称是建议，不是预建分支。每个PR只覆盖可审查的一段；共享contract变更先与依赖团队对齐。源码参考保留来源和修改说明。

技术负责人负责规划和审查，执行由工程师完成；安全关键PR由非实现作者复核。项目负责人拥有范围和视觉方向变更决定权。包内没有指定任何真实人员为负责人或审批人。

## 4. 变更分级

不改变行为的内部重构、修复和测试补齐：在PR记录即可。

改变API/schema或可调阈值：提交技术依据、影响、测试与迁移，由技术负责人评审；保持用户已定边界。

改变自治/权限、数据出域、默认模型、恢复策略、单主会话、记忆所有权、看板复用路线或角色形象：使用CHANGE_REQUEST模板，取得产品确认后形成新基线。

任何G03/G04/G05安全前提不能用进度压力或“只给自己用”绕过。可明确发布只读诊断，但不得称完整写模式已实现。

## 5. 对用户真实环境的操作

开发授权不等于对真实项目执行操作授权。首次接入真实历史、启用真实Session派发、开启渠道与生产部署分别说明范围；不把用户旧对话中的批准当作当前许可。

本包不自动创建仓库、不发送消息、不配置机器人、不操作服务器、不安排自动监控。
