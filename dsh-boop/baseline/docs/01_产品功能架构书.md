# BOOP（波波）产品功能架构书

> 版本：1.0 · 日期：2026-10-16 · 产品：DSH 原生个人项目助理  
> 状态：可评审设计基线，不代表已实现或通过运行验收。技术常量以第 03 册为准；外观以第 05 册为准。

## 01｜执行摘要

BOOP 是当前用户 DSH 工作世界的个人项目助理。用户面对一个持续身份、一条长期主聊天；BOOP 帮用户定位既有工作区与 Session，接受任务委托，协调原 Agent，跟踪交付与验收。系统在源头自动维护各 Session 的工作记忆，再形成工作区项目记忆。BOOP 按需读取，不重复消化全部历史，也不替换原 Agent 的执行引擎。

**一句话承诺：你不用记住每条 Session 在哪里、上次做到哪里；波波帮你找回工作现场，在明确授权内推进，并说明结果和证据。**

产品不是多 Bot 群聊平台，不是另一套项目管理软件，不是生活管家，也不提供突破其他用户、其他 Host 或操作系统隔离边界的“全局权限”。

### 已确认与设计建议分开

| 事项 | 已确认边界 | 本版设计默认值 |
|---|---|---|
| 名称 | 最新命名为 BOOP（波波），替代讨论期 Bloop | 包名候选 `dsh-boop`，是否可注册待发布前查询 |
| 宿主 | 本地 DSH Web 与 Desktop；0.2.0-rc.2 | 两端共用 Web 客户端与 Host 插件；首验 Windows，再扩展 macOS/Linux |
| 模型 | 用户自有服务器 `qwen3.8-27b`，4bit，上下文 196k | 主对话、受限记忆整理共用已授权路由；不自动切外部供应商 |
| 主入口 | 一个身份、一条用户可见主聊天 | 普通工作仍留在原 Session，不创建项目级 BOOP 分身 |
| 记忆初始化 | 新开始／历史学习／导入，初次对话可选 | 未选择时不启动历史全文整理；目录清单可以先展示 |
| 资源 | 不计模型费用 | 不做计费页；保留并发、超时、队列、循环防护 |
| 消息 | 会话内消息，不另造通知中心 | 待决项放任务看板筛选，主动结果合并进入主聊天 |
| 外部渠道 | 要考虑钉钉、飞书机器人双向互动 | 作为可选适配器；首版仅已绑定本人单聊，默认关闭群聊与远程危险审批 |
| 发布 | 先个人使用，后续开源 | 独立仓库、外置配置、来源台账、发布前许可审查 |

DSH 的实际发布 tag 是 `dsh-v0.2.0-rc.2`，本版核验提交为 `639ed015397290b3745d163aafe02ffee4aa3f84`。不能使用后续 master 的功能替代该基线。[S01]

## 02｜成功标准与非目标

### 成功标准

1. 找回工作：用户用项目描述即可抵达正确的既有工作，而不是再解释一遍背景。
2. 委托可追踪：派发、接收、执行、验收可区分；不存在“消息发了＝工作完成”。
3. 记忆少维护：不依赖每个 Agent 自觉写报告，用户纠正后不会被旧来源立即覆盖。
4. 控制不丢失：用户对原 Session 的最新有效指令优先；未知结果不重试写操作。
5. 低干扰：BOOP 的对话和业务可用性不被后台历史整理长时间占住。

### 第一版明确不做

全局共享大脑、自动管理所有未委托 Session、自动重启中断业务、多人团队权限平台、云端同步与多 Host 联邦、专属浏览器或专属分屏、完整 GitHub/Jira 替代品、无条件自动回滚、费用账单、Feed/资讯推荐、普通 Session 的人格或默认模型改写。

主聊天和任务看板是同一产品的两种视图，不另增收件箱产品。归档、删除、停止、取消委托是不同动作。

## 03｜产品信息架构

```text
DSH 原生界面
├─ BOOP 固定入口
│  ├─ 主聊天：对话、查询、委托、合并汇报、上下文卡、明确审批
│  └─ 任务看板：全部受托工作／进行中／待我处理／已结束
├─ 原有 Workspace 与 Session：实际开发、分析、研究、工具过程
└─ 原生设置 → BOOP：模型路由、记忆覆盖、观察范围、渠道、安全、数据管理
```

主聊天默认展示最近对话。只有需要精确确认时，才显示任务、记忆冲突、候选对象或审批卡。看板可从头部进入；返回后保留主聊天草稿、阅读位置和当前任务语境。不把全局看板塞进每个原 Session 的右侧栏。

原生 Conversation 在 rc.2 已有 Session 输入、历史和扩展位；全局 `main` keyed slot 可承载独立看板。BOOP 复用这些能力，而不复制另一套聊天编辑器。[S05][S06]

## 04｜角色、对象与责任

| 对象／角色 | 负责什么 | 不负责什么 |
|---|---|---|
| 用户 | 最终意图、授权、取消、纠错、验收豁免 | 不需要手工维护全部任务和记忆 |
| BOOP 主 Agent | 理解、查找、协调、提出动作、解释结果 | 不是授权数据库，不保证外部动作可逆 |
| 原 Session Agent | 在其原环境内执行任务，提供工作证据 | 不直接改写 BOOP 全局政策 |
| 任务控制器 | 委托版本、状态、动作、依赖、恢复与验收记录 | 不依赖模型一句完成来自动放行 |
| 记忆流水线 | 受控提取、版本提交、项目聚合、纠正传播 | 不向业务 Session 发“继续执行” |
| Workspace | 默认项目归属与原生目录关联 | 不天然等于一个长期任务 |
| Task | 用户明确交给 BOOP 的工作承诺 | 不等于一次 Turn 或一条 Session |
| Action | 一次带范围、身份和前提的派发／变更 | 不等于无限授权 |

一项 Task 可关联多个 Session；一条 Session 可先后处理多个 Task。跨 Workspace Task 通过关联表达，第一版不让用户再维护一套项目实体。原始工作区名改变不改变任务身份。

## 05｜功能地图与追踪编号

| 编号 | 功能域 | 核心交互与产出 | 成功条件 |
|---|---|---|---|
| FR-01 | 安装与固定身份 | 创建或找回唯一 BOOP 主聊天 | 并发打开不重复创建；不改全局默认 Preset |
| FR-02 | 初始化记忆 | 新开始、历史学习、导入三选一；以后可补充 | 不隐式恢复旧任务，覆盖范围真实可见 |
| FR-03 | 项目查询与 RAG | 指定项目直读、模糊描述检索、证据下钻 | 先权限与归属，再相关性；关键限制强制带回 |
| FR-04 | 工作区与会话管理 | 列举、创建、改名、归档、恢复、定位 | 原生能力内操作；目录删除独立审批 |
| FR-05 | 任务委托 | 理解目标、去重关联、确立完成标准 | 讨论不自动成为执行任务 |
| FR-06 | 跨 Session 指挥 | 排队、补充约束、取消待发动作、请求停止 | 来源可辨识；执行与聊天回执分离 |
| FR-07 | 跟踪与验收 | 证据、失败、豁免、有限自愈 | 状态与所验证版本一致 |
| FR-08 | 任务看板 | 受托工作和待决事项 | 与聊天同一任务数据，无第二套状态 |
| FR-09 | 源头工作记忆 | 每轮变化登记，增量提取与工作区汇总 | 游标可续、可纠错、保留来源 |
| FR-10 | 主动节奏与巡检 | 重要变化触发、一般进展合并 | 不依赖持续全量模型巡检 |
| FR-11 | 中断与恢复 | 重启对账、等待明确恢复 | 记忆补齐可继续，业务执行不可偷偷继续 |
| FR-12 | 安全与审批 | 委托范围＋原生工具两道门 | 记忆、模型输出、外部文本均不能授予权限 |
| FR-13 | 多渠道 | Web/Desktop、钉钉/飞书本人单聊 | 同身份同任务，不广播全部主聊天 |
| FR-14 | 数据与停用 | 排除、忘记、导出、停用、卸载 | 不删除项目文件；说明残留执行与备份副本 |

## 06｜委托如何成立

“以后可以做三分屏”是候选想法；“调研三分屏”是研究任务；“实现三分屏并验收”是执行委托。普通问答与一次性检索不强制建 Task。只有需要跨 Session 行动、持续跟踪或未来执行时才建立受托工作。

BOOP 在一次确认式回执中说明目标、目标对象、完成标准、禁止项。例如：“我会继续原开发会话，按当前方案实现并检查窄屏效果；不合并、不部署。”这条回执不能自行扩大用户原指令。对象不明或范围存在冲突时只问必要的一次。

已有同范围活跃任务优先更新，不重复建卡。相似名称不等于同任务；合并任务须有相同目标和证据，不能只凭向量相似度。

## 07｜任务、执行、验收三条状态轴

| 状态轴 | 值 | 用户理解 |
|---|---|---|
| task.lifecycle | draft / active / paused / blocked / recovery_required / completed / cancelled | 这项委托目前是否继续 |
| action.execution | planned / awaiting_approval / dispatching / accepted / running / settled / stopped / outcome_unknown / rejected | 这次动作到哪一步 |
| task.verification | not_requested / pending / passed / failed / waived | 结果是否经验证 |

`completed + passed` 显示“已完成”；`completed + waived` 显示“已结束 · 用户决定不再验收”，不显示绿色验收通过。只收到原 Agent 口头完成时仍是待验收。工具超时或无回执进入 `outcome_unknown`，先核查，不重发。

产品默认：实现不包含合并，合并不包含部署，调研不包含开发，创建工作区注册不包含删除/迁移目录。每次跨阶段需要任务范围原本明确包含或用户追加委托。

## 08｜验收不只面向代码

| 类型 | 最小证据 | 不能据此宣称 |
|---|---|---|
| 开发 | 精确分支/提交、测试名称与结果、必要交互核查 | 单元测试通过＝所有体验无缺陷 |
| 分析 | 数据源、时间口径、公式/SQL、交叉校验、产物位置 | 文件生成成功＝经营结论正确 |
| 研究 | 范围、来源日期、主张与证据对应、未解项 | 有摘要＝研究充分 |
| 整理 | 计划清单与实际成功/失败列表 | 部分成功＝全部完成 |

同一个模型再次评阅不能称作独立审计。可用相同模型做第二视角检查，但必须标明证据类型和未覆盖项。验收前项目内容变化，相关证据失效或需重新核查。

## 09｜唯一主聊天的持续性

身份、聊天、任务、记忆的生命周期分开。关闭页面不取消任务；清理显示不删除记忆；归档普通 Session 不删除其执行事实；BOOP 主聊天异常不意味着委托账本消失。

默认沿用原生 compaction，按需历史回读。不在 v1 包装替换压缩引擎。真正需要迁移主 Session 时，保留逻辑身份并通过维护操作重新绑定，旧记录可追溯，迁移不携带隐含执行授权。DeepSeek-Bot 的透明分段是参考方向而非本版必需实现。[S10]

聊天 Stop 只停当前 BOOP 回答；暂停任务关闭未来派发；终止任务请求停止已关联执行；全停按钮收紧全部 BOOP 委托，不能停止未受托工作。取消请求成功不等于工具副作用已撤销。[S02]

## 10｜记忆初始化与日常学习

### 新开始

以选择时的可读事件边界建立水位；以后只整理新增内容。旧 Session 后续继续说话时，必要前文可以作为理解背景读取，但不悄悄全量导入历史。日后用户选择历史学习，另外建立可暂停批次。

### 历史学习

先列目录，再按近期活跃项目排队。展示待处理、已处理、排除、失败、尚未验证来源。百分比来自清单处理量，不代表理解正确率。重启可继续只读学习任务，但不能恢复历史业务任务。历史中的“批准部署”只作为当时的事实，不生成现在的授权。

### 导入

首版接受 UTF-8 Markdown、TXT、BOOP 导出的带版本 JSON 包；不直接执行导入文件，不从路径字段读取任意本地文件，不解压不受限压缩包。导入内容先预览数量、来源和潜在重复，标为 `import/unverified`。个人偏好与项目资料可分别归类，权限规则不随记忆导入。

### 日常

执行事件 → 变化登记 → 受限增量整理 → Session 工作记忆 → 工作区项目聚合。执行 Agent 可以提供纠错证据，不能直接获得全局记忆写权限。记忆流水线参考 BOT 的游标和失败处理，聚合规则为 BOOP 自研。[S09]

## 11｜观察、管理与主动交流

| 变化 | 是否深度理解 | 是否采取业务动作 | 是否发主聊天消息 |
|---|---|---|---|
| 未受托 Session 普通变化 | 合并后更新工作记忆 | 否 | 否 |
| 受托执行正常进展 | 必要时 | 范围内可继续 | 默认不发 |
| 完成一阶段 | 证据核查 | 按已授权阶段推进 | 合并汇报 |
| 用户修改有效指令 | 立即核查受影响任务 | 撤销旧待发指令 | 影响重大才说明 |
| 等待审批／恢复 | 保存精确待决对象 | 未批准不执行 | 一条待决消息，之后更新同项 |
| BOOP 不可确认状态 | 保留不确定性 | 停止新的危险派发 | 涉及当前任务时明确说明 |

没有独立通知中心、没有系统推送。消息均归唯一主聊天；看板提供同一任务的“待我处理”筛选。普通事件不形成可见对话；关键汇报和审批作为持久消息留痕。用户阅读历史时不自动滚到底部，新增消息使用会话内位置提示。

## 12｜钉钉与飞书的产品范围

这不是“发个 Webhook 通知”。双向交互需要应用机器人及消息接收能力。钉钉官方 Stream 支持机器人收消息和互动回调；飞书官方 SDK 提供平台 API 与事件接入基础，具体连接与权限按实施时 SDK 核验。[S24][S25]

默认一对一绑定用户。来自未绑定身份、其他租户或群聊的内容不进入可执行委托。渠道仅提供已验证的身份信封，用户正文不能伪造 source、taskId 的权限或审批人。

所有渠道的消息最终串行进入同一 BOOP 主聊天；回复发回来源对话，重要结果也落在 DSH 历史。不会把完整主聊天镜像到所有渠道。高风险审批首版回到 Web/Desktop 精确确认；远程可以查询、委托允许的低风险工作、暂停和提交明确的恢复请求。Host 关闭时无处理能力，不承诺手机消息必然实时执行。

## 13｜安全默认行为

被授权观察的内容可送到用户指定模型服务；不因“模型本地/自有”就忽略服务器与客户端之间的数据传输。TLS/VPN/访问密钥属于接入验收。禁用远端回退模型。BOOP 默认无任意 Shell、文件写入、插件管理及凭证读取工具；需要业务执行时交给原 Agent，并保留原 Session 工具权限。

观察授权不等于管理授权，任务授权不等于危险操作许可。权限提升、部署、批量删除、导出敏感数据、改模型目的地等不能仅凭聊天摘要完成。安全规则不由自主学习自动改写。

## 14｜本地 Web 与 Desktop 的一致性

同一个 DSH Host 的多个页面共用 BOOP。不同 Host 同时访问同一 BOOP 数据域时只允许一个有效控制者，其他端只读并解释原因；不能同时驱动同一个主 Session。不同 DSH_HOME 默认是不同本地数据域，不承诺自动合并身份历史。通过显式导出/导入迁移，不让用户在不知道的情况下出现两个控制者。

这不改变“一个 BOOP”的产品心智：单数据域一个身份、一个主聊天、一个任务账本。跨 Host 同时在线协同不是 v1 范围。

## 15｜发布分层，不把未实现能力藏起来

| 里程碑 | 必须交付 | 不满足时表现 |
|---|---|---|
| M0 基线验证 | rc.2 加载、模型路由、原生 UI、消息来源、权限、持久化 PoC | 写操作保持禁用 |
| M1 个人可用核心 | FR-01～12、14 的基础闭环；本地 Web/Desktop | 每项缺失能力在设置内明确 |
| M2 可选 IM | 钉钉与飞书本人单聊，端到端去重与身份绑定 | 未配置不外连；不以单向通知冒充双向 |
| M3 开源发布 | 来源许可、文档、兼容矩阵、数据迁移、安全回归 | 不发布兼容豁免当作稳定支持 |

M1、M2 均有完整设计；分阶段不代表取消渠道需求。不要为了发布一个“全功能”版本而同时启用尚未验证的写权限。

## 16｜产品验收与衡量

必须通过：同名任务准确定位、人工介入优先、历史初始化不恢复旧任务、派发超时不重复写、模型不可用仍能停止、审批失效不能重用、关闭重启不会自动恢复业务、退出/停用不会污染原生 Session、导入内容不能授予权限。

质量指标是设计验收目标，不是实测结果：本地不调用模型的页面交互 P95 < 200ms（约定设备与数据量）；会话内通知可被用户理解；模型耗时单独呈现，不以硬件未知的秒数承诺。记忆效果用真实项目金标集测量：有效决定遗漏、旧决定误用、来源可回查率、任务恢复准确率。安全发布样例中未授权执行应为 0；这不表示生产绝不会出错。

最终成功是用户减少检索、重复交代和协调成本，同时不被迫每天维护 BOOP 的记忆和待办。
