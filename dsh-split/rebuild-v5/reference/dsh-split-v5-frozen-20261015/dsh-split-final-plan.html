01 · 架构复核结论

1.1 “合理、高效”的具体含义

在已确定的目标下，推荐采用“一个外层 Dockview＋每会话一个轻量内部分栏＋DSH 原生内容适配”。它减少重复布局状态、避免重复业务实现，并把兼容风险集中在一个版本明确的接入边界。

这是一项在当前需求和证据下的工程取舍，不是“所有实现中绝对最优”的证明。原生运行性能、不同平台的拖拽和热卸载安全，仍以真实 DSH 集成测量为准，不能由低保真 Demo 推断。

决策 为什么采用 明确不采用
一个完整会话对应外层一个 Panel；每个 Group 仅容纳一个会话 移动会话时正文、Sidebar 和绑定一起移动；没有额外标签管理 Conversation 和 Sidebar 作为两个全局平级 Panel
只在外层使用 Dockview 复用成熟的几何、约束和布局序列化；业务不自写布局树 自建生产级二叉树＋GridDom；实时维护第二份可写几何状态
会话内使用 CSS Grid＋方向／比例 主体只有正文和整块 Sidebar，不需要第二个完整停靠引擎 每个会话再装一套 Dockview
Sidebar 内部仍由 DSH 管理 保留 Tab、provider、保活、终端恢复和关闭语义 复制文件树、终端、浏览器或 Tab 生命周期
一个合法呈现宿主，单会话与多会话同构 一变二、二变一不切换架构，不抢编辑器 覆盖层盖住另一份仍挂载的原生会话
Claude 仓库作为交互和视觉参考 借鉴层次、标题拖拽和克制反馈；不依赖未经验证的实现 整包导入逆向组件，替代 DSH 原生业务

Dockview 的 Panel／Group 结构、渲染策略和移动 API 适合外层布局；但使用哪些行为应由产品约束决定，不把库支持的所有特性都开放。[S1][S2][S3]

1.2 本次不做

不新增“并排打开”第三个按钮；不做跨会话标签合并、替换模式、最近使用 Group、空格占位工作流。没有独立 Sidebar 窗口、跨会话 Sidebar 拖动、自由浮窗、系统弹窗、多屏弹出、命名布局模板、布局撤销重做、跨设备同步、模型自动整理布局、任务中心或通用面板市场。

这些限制只针对本插件新增能力，不删除 DSH 原生 Sidebar 内已有的标签与内容功能。菜单中的方向操作是拖拽的键盘替代入口，不是另一种产品模式。

02 · 产品结构与视觉层级

2.1 一层会话，两块内部内容

DSH 原生导航与应用外壳
└─ 多会话工作面
   ├─ 会话 A：统一圆角容器，无边框线；非当前时覆盖极淡浅灰遮罩
   │  ├─ Conversation A：原生正文、View、Composer
   │  └─ Sidebar A：带边框的辅助面板，内部保留原生 Tabs
   └─ 会话 B：同样结构
      ├─ Conversation B
      └─ Sidebar B

Sidebar 的业务归属始终是 Session，而不是位置。 即使 A 从左侧移到下方，A 的 Sidebar、输入框和正文仍然是一组。Sidebar A 不能拖到 B 的内部。

Claude 官方资料确认了标题拖动、边缘缩放和网格排列；逆向仓库主要提供局部分栏及组件线索，不足以证明完整的内部布局树。本方案的“两层结构”是针对用户已确认需求的设计，不声称复制了 Claude 内部源码。[S4][S5]

2.2 圆角承载与极淡聚焦

区域v5 视觉规则
A、B 整段会话有完整圆角承载面，与 Sidebar 共享 --session-radius / --radius 初值 12px；外壳不画边框线、不加阴影。标题、正文、Composer 和本会话 Sidebar 一起位于圆角范围内。
正文和会话工具区不再包第二层卡片；使用与原生 Composer 遮罩相容的背景。圆角容器不意味着每个内部部分都必须有外框。
会话之间仅保留间距，不绘制会话间分割线，悬停和拖动时也不重新画线。保留透明的尺寸调整命中区、方向光标、拖拽、双击均分与键盘尺寸操作；这不是删除分屏或调整尺寸能力。
Sidebar保留细边框和同一圆角变量；增加一层轻微、静态的悬浮阴影，不随焦点加深，不扩散成厚重光晕。右上角的停靠位置与关闭图标按钮移除；标题继续可拖动，点击标题或按 Enter 可选择停靠方向，收起使用会话标题栏原有 Sidebar 按钮。
当前会话没有遮罩、没有厚边框或聚焦阴影；按钮自身仍保留键盘无障碍焦点提示。
非当前会话在整段会话表面覆盖一层极淡的浅灰色；保留文字、按钮、预览可读性，不使用整体 opacity 或滤镜。
拖动期间临时落点预览与拖动标签，结束即消失；不改变内容实例身份。

该遮罩只表达“当前操作对象”，不代表会话暂停、禁用、断线或没有权限。没有 focusin 时不把全部会话一起蒙灰；窗口内始终保留最后明确激活的会话。应用失焦不触发另一套整页变暗效果。

Sidebar 阴影：浅色初值 0 1px 2px rgba(24,28,21,.035), 0 4px 12px -4px rgba(24,28,21,.065)；深色适度增强黑色阴影以保持可见但克制。只应用于 Sidebar，自有内容宿主允许阴影进入既有留白，外围会话仍保持圆角裁剪。阴影不影响尺寸、不参与焦点状态，也不为整个会话增加阴影。

2.3 微调的保留与重新取舍

保留统一间距节奏、原生底色一致、浮层不被裁切、系统标题栏正确避让和 reduced-motion。会话和 Sidebar 的圆角必须共享一个 token，不能分别写死后逐渐出现差异。v5 初值均为 12px；会话边框和聚焦阴影为 0。

非当前遮罩在 Demo 中采用浅色 rgba(140,148,157,0.075)、深色 rgba(162,170,180,0.045)。这只是体验初值，不是 Claude 实测值；生产按原生底色和对比度校验微调。遮罩为独立伪元素、pointer-events:none，只改变自身透明度，绝不设置根组件 opacity、filter 或 inert。

主要目标是首次点击就能直接操作：点击非当前会话的输入框应当同时激活并放置光标，不要求先点一下“解锁”；触摸、Tab 聚焦、Sidebar 终端和嵌入网页也是同一规则。菜单、灯箱、审批等全局浮层由原生 portal 管理，不被该遮罩和圆角裁掉。

不强制 30px 标题高度、不把所有间距机械统一为 10px。原型仍保留约 45px 会话标题、36px Sidebar 标题和 12px 透明间距命中区。左侧每个会话条目提供清楚的 ⋯ 入口；不要将复杂操作重新塞回会话标题栏。

03 · 完整交互合同

3.1 分屏与会话选择

操作明确结果必须避免
点击左侧 B 的 ⋯ / 右键菜单只打开 B 的选项。捕获当前会话 A 作为参照，菜单归属 B 作为目标。先普通导航到 B，导致分屏来源漂移。
B 菜单 → 向右分屏直接在 A 右侧显示 B；A 保持原位置和内容。不再显示会话选择器。同一功能同时出现在会话标题和目录；要求再选一次 B。
B 菜单 → 向下分屏直接在 A 下方显示 B；规则与右分屏相同。误当成复制 A；偷偷改变分屏方向。
取消菜单 / Esc关闭菜单，焦点返回对应 ⋯ 按钮，原布局与活动会话不变。留下空窗格，或把目录菜单的焦点当成会话切换。
B 已在当前工作区显示菜单提供“定位此会话”；右／下分屏禁用并解释“不重复创建”。用户可用标题拖动改变已有 B 的位置。第二个相同 Session 的可编辑 Composer；隐式移动已打开的 B。
没有当前会话 / 空间不足 / 临时放大分屏禁用并给出原因；没有参照时先正常打开一个会话。为了执行菜单动作临时切走当前会话或创建空格。
原生“新建会话”保留原生入口与创建行为；创建后在当前位置打开；需要分屏时由其列表菜单执行。重新引入会话内的分屏选择器。
普通点击目录中未显示的会话在当前明确激活的窗口中切换；被替换的会话仍保留记录与草稿。自动创建会话标签组。
普通点击目录中已显示的会话只定位并激活已有窗口。重复打开。
关闭会话 / 临时放大 / 恢复保留原有视图生命周期；关闭视图不删除 Session，放大只隐藏其他窗口。停止 Agent、误关 Sidebar 资源、另建宿主。

唯一操作入口：原生左侧会话列表的逐行菜单。菜单动作名称仍是“向右分屏”“向下分屏”，不额外增加“并排打开”。会话标题保留移动、Sidebar、放大和关闭，不能再出现分屏按钮或第二次选择对话框。

生产动作建议捕获 { anchorPanelId, anchorBindingEpoch, targetSessionId, direction }。异步准备目标时若参照已关闭、已换会话或菜单意图过期，则取消该布局动作并保留合法创建的会话。菜单所属的目标不能随全局 current 改变。

接入应复用 DSH 该版本实际提供的会话菜单扩展契约；若缺少稳定入口，列入已授权的宿主适配补丁，不复制整套目录，也不通过 DOM 注入一个脆弱按钮。原生列表的其他选项继续保留。

3.2 移动整个会话

拖动会话标题空白区域或把手；按钮、菜单、正文选择和 Composer 不触发外层拖拽。标题区域同时提供可访问的方向移动菜单，供键盘或触摸使用。

  1. 按下时只捕获手势起点；超过小阈值才进入拖动。正常单击不变成拖动。
  2. 保持原内容在原处，显示轻量预览标签，例如“会话 A · 整体移动”。不拖着整块实时 transcript 绘制阴影快照。
  3. 鼠标进入另一个会话的左、右、上、下落区，显示提交后 A 真正占据的范围。先计算移除来源后的目标，不预览不存在的第三块空位。
  4. 鼠标移动只改变预览；松手才向外层引擎提交一次移动。原空位由引擎合并。
  5. 中央不是合并、覆盖或复制落点；会话目录和应用外部也不是落点。无效处松手不改变任何布局。
  6. Esc、pointercancel、失去有效捕获或窗口失焦取消手势，清理遮罩和光标。取消不触发原生停止操作。

结果示例：A 左 B 右时，把 A 拖到 B 的下方，应变成 B 上 A 下。A 的 Sidebar 方向、比例、内容、消息与草稿随 A 保留。移动期间不交换 sessionId，也不通过 remove＋add 伪造移动。

3.3 Sidebar 的位置与大小

整个 Sidebar 是原生辅助内容的单一宿主。通过其标题拖动，在所属会话内左／右／上／下停靠；默认右侧。点击或用键盘激活 Sidebar 标题打开方向菜单，与拖动走同一条操作；标题栏右上角不再额外放停靠和关闭图标。

Sidebar 内部标签拖动仍属于原生 Tab 层，不能冒泡为整个 Sidebar 的移动。首版不外置单个文件、终端或浏览器 Tab。

行为 合同
在本会话内改变方向 只更新方向，不关闭再打开 Sidebar，不改变原生 Tab 身份
拖到其他会话 拒绝；其他会话不显示 Sidebar 接收目标
收起 Sidebar 只隐藏辅助区域，正文获得空间；保留 Tab 和资源持有
展开 Sidebar 恢复该会话上次方向和比例
打开会话 A 的文件 走原生资源认领与导航，在 Sidebar A 展示；不受 B 当前焦点影响
调整分隔条 实时跟手；只影响本会话；达到尺寸边界时停止
双击分隔条 在约束允许时均分；不可用时按最小尺寸钳制
窄到无法同时容纳 在该会话区域投影为单内容显示，提供“返回对话”；不遮盖整个应用

水平、垂直比例分别记忆，避免从右侧移动到下方时把一个“宽度比例”不合理地当作“高度”。不做拖窄自动关闭，用户只通过明确按钮收起。

原生终端例外必须正确保留：收起 Sidebar 不停止终端；显式关闭或替换终端 Tab 会触发原生资源清理。 不把所有关闭动作统一解释为“只关视图”。[S8]

3.4 尺寸、文字和焦点

会话之间的透明间距用于调整相邻会话，内部接缝用于调整正文与 Sidebar；外层不绘制分割线，两个命中区域仍然分离。尺寸即时跟手，不对连续宽高叠加长过渡或弹簧。移动整个会话不主动聚焦 Composer。

聚焦来源：会话范围内的 pointerdown、focusin，以及经宿主验证所属关系的 iframe/浏览器焦点。变更 activeSessionId 只切换轻灰遮罩，不重建会话、不重新打开 Sidebar。输入法组合输入、选区与原生快捷键交还原生。

同源 iframe 可以接合适的原生焦点事件；隔离文档只能通过受控消息或宿主焦点桥接。必须验证消息来源与已挂载的 iframe/host 对应，不接受任意页面仅凭自报 sessionId 激活目标。Demo 的本地 sandbox iframe 使用固定消息类型，并以 event.source === ownedFrame.contentWindow 校验；不依赖任意 origin 通配消息来决定业务身份。

遮罩不阻止任何第一次点击；active 会话之外的输入区域、按钮和文件拖放仍正常可操作。打开左侧菜单不改变 current，关闭菜单不把全部会话变灰。单视图、临时放大和窄屏下实际显示的会话保持清晰。

文件只由明确的会话接收一次。发送、上传、审批、终端和原生标签关闭仍捕获 Session/occurrence；异步失效不回退全局 current。布局和聚焦不是权限机制。

04 · 生产实现：三个职责边界

DSH 原生 AppFrame / 原生导航 / 系统 chrome

       WorkbenchHost + 单一外层 Dockview
          面板目录 / 方向动作 / 外层快照
                     │
      SessionSurface(panelId, SessionReference)
          轻量标题 + 会话内 CSS Grid
             ┌───────┴────────┐
     ConversationBridge    SidebarBridge
      原生 Factory、View、  原生 Tab 域、provider、
      Header、Composer      keepMounted、关闭语义
             └───────┬────────┘
               DSH 原生状态与执行

这里只新增布局与宿主适配，不建设另一套 Session Store、消息服务、任务调度器或文件协议。实际工程中不必把每个名字都独立做成一个包；首先保持这三个边界，避免过度模块化。

4.1 外层：Dockview 的受限使用

一份 Dockview 布局；每个会话只占一个 Panel；每个 Group 只装一个会话。禁止中心／标签合并目标、浮动、popout 和跨工作区拖入。不显示 IDE 式会话标签栏，会话标题仅提供整体移动、Sidebar 显隐、临时放大和关闭视图。分屏入口只在左侧具体会话的选项菜单中。

优先使用公开的 addPanel、面板移动、尺寸约束、最大化、布局事件和 toJSON/fromJSON。普通操作绝不每次通过 fromJSON 重建全部页面；恢复仅用于初次加载、明确重置或错误恢复。[S1][S3][S9]

精确的拖动策略在锁定版本中验证：优先收窄内建 DnD 的目标；若内建方式无法达到预览和取消合同，可使用一个小型 Pointer 手势适配器，仅输出方向移动意图，再调用公开移动 API。不复刻 Dockview 布局树、不维护生产用像素引擎。

locked、disableDnd 等配置的实际语义以被锁定版本为准；不能假定“隐藏标签”就同时阻止了标签合并。配置之外再对新增／移动后单 Group 单会话的不变量做断言。具体 Dockview 包版本在原生原型通过后写入 lockfile，不以文档网站当前主版本替代验证。[S10]

4.2 内层：只需要一个 CSS 分栏

每个 SessionSurface 的子节点保持稳定：正文、分隔条、Sidebar。改变 side 时通过 CSS Grid 的行列与区域分配改变几何，不通过移动、删除、重新插入 iframe 或 React 子树改变排列。

Sidebar 隐藏可以改变可见性和占位，但不能清空原生 Tab 记录。保持 DOM 不是无限保留所有会话页面：只保留原生 provider 明确要求的内容，仍由原生保活所有者管理后台资源。

Sidebar 内已有的 dockkit 是内容提供系统的内部实现，不把它扩展为第二个“全局工作台”。它与外层 Dockview 的拖拽范围、尺寸坐标、层叠以及快捷键要隔离。嵌入态的 fullscreen 应通过宿主呈现语义实现，不能再覆盖整个多会话页面，也不能同时启用两套最大化状态。

4.3 状态由谁持有

状态 唯一所有者 可否存进外层布局
会话消息、草稿、模型、运行状态 DSH 原生 Session／Conversation 不复制
Sidebar Tab、内容地址、导航、终端身份、关闭流程 DSH 原生 Sidebar／provider 不复制
哪些会话窗口打开、当前明确目标 插件工作台状态 可保存安全引用
会话间位置、尺寸、分割关系 Dockview 由引擎快照保存
Sidebar 外部停靠方向、横纵比例 插件逐 Session 呈现状态 单独保存，不写进原生 Tab 几何
pointer 坐标、拖动候选、预览、取消控制器 当前手势的临时状态 不保存
手机／窄窗口临时单视图 呈现投影 不覆盖桌面几何
最大化状态 临时呈现状态 默认不恢复最大化，保留底层几何

建议模型只需要少量字段，以下均为新增设计类型，不是现成 DSH API：

type SidebarSide = 'left' | 'right' | 'top' | 'bottom';

interface SessionSurfaceRecord {
  panelId: string;       // 几何对象身份，不由行列或焦点派生
  sessionId: string;     // 实现时使用 DSH SessionId 类型
  bindingEpoch: number; // 显式切换会话时递增，移动／缩放时不变
}

interface SidebarPlacement {
  side: SidebarSide;
  horizontalRatio: number;
  verticalRatio: number;
}

panelId 和 sessionId 不混用：移动同一窗口保留二者；显式切换会话保留位置但更换会话绑定并使旧异步 UI 意图过期。同一 Session 在整个窗口范围内只能有一个可编辑呈现根，包含可能存在的原生 subagentchat。

05 · 原版 rc.2 的接入边界：不能承诺纯热插拔

5.1 已核实的事实

Conversation：conversation.content 已支持可复用嵌入；主 Header 在 Factory 外部；同一 Session 的 Lexical 编辑器不支持多个同时挂载的可编辑 root。[S6]

Sidebar：其初始化代码通过选中 Session 与 activePanelId === null 决定显示目标，同时向传统右轨道报告宽度。它尚不是任意多个可见会话宿主的通用面板服务。[S7]

资源语义：Tab 记录、保活、显式关闭和终端恢复有自己的原生所有者。保持这些边界比“复制一个 Sidebar React 组件”重要。[S8][S11]

上传旧包的 README 和交付 bundle 描述了覆盖层与下方原生输入根竞争、generation 重挂等补偿。这只作为需要消除的风险，不继续继承相应机制。来源为用户上传 dsh-split.zip；先前审计是静态核对，不是运行测量。

5.2 推荐交付形态

插件主体＋必要时经用户确认的、锁定 rc.2 的小范围前端契约补丁。 当前交付没有修改任何原生文件。

“能停用插件”“运行时可热卸载”“完全不修改原版”是三种不同承诺。若后续以公开接口证明全部需求可实现，则保留纯插件路线；没有通过证明前，不在安装说明中写“原版零改动热插拔”。

需要的契约 推荐调整位置 不触及的范围
主内容有且只有一个生效的呈现宿主；原生设置等全局面板仍正常 ui-layout 与 Conversation 的宿主组合 Agent 执行、服务端协议
原生 Header／View／Composer 能合法嵌入每个 SessionSurface ui-conversation 的装配契约 复制私有编辑器、另做聊天组件
Sidebar 显式绑定 Session、宿主尺寸与可见性，不只依赖全局 current ui-sidebar-right 的内容与 frame 呈现分离 重做 provider、终端 controller
焦点、快捷键与附件接收只命中所属会话 原生上下文注入／命令入口 插件另起全局发送系统

上表是拟修改边界，不是确认的文件数与补丁行数。Slot 的授权与声明规则应保持，必要时补公开 Factory 或宿主契约，不通过 DOM 查询搬运、私有 import、同名 Slot 抢占或运行时 monkey patch 绕过。

5.3 上线阻断条件

P0 原型必须先验证上述边界。若无法实现唯一编辑根、完整原生功能或两个 Sidebar 的独立目标，就不进入视觉集成阶段。没有授权，不自动落原生补丁。

首次安装补丁通常需要更新客户端产物并重新加载。插件热启停作为独立验收项：不销毁运行任务、资源不被误关、原生视图可恢复。未通过前只支持明确的受控切换／重载，不把热卸载当默认保证。

06 · 生命周期与事件顺序

6.1 不能省略的四条不变量

唯一编辑根：同一 Session 同一时刻只有一个合法的可编辑 root。隐藏在下方仍挂载的页面也算一份，不能用 CSS 视为“已移除”。

目标不漂移：发送、上传、文件打开、审批、终端命令捕获自己的 Session／Tab 身份。布局位置不能成为权限或业务身份依据。

移动不等于销毁：外层移动和内层换边不调用关闭资源的 API，不重新创建 Terminal 或打开一个新的同地址 Tab。业务组件的 key 不由 Group、方向或焦点派生。

隐藏不等于结束：关闭会话视图、收起 Sidebar、临时放大、浏览器暂时隐藏，都不自动发送停止 Agent／关闭内部资源命令。显式关闭终端 Tab 仍执行原生清理。

6.2 会话切换是一笔明确事务

捕获来源 Panel 与 bindingEpoch → 通过原生机制准备目标 SessionReference → 确认目标未被其他可编辑根持有 → 检查该导航仍有效 → 释放旧视图绑定，提交新绑定 → 更新明确焦点。

已经显示的目标会话直接定位，避免重复占用。异步准备期间若用户关闭来源或另选会话，旧导航不得把新会话塞进一个意外窗口，也不能删除已经合法创建的 Session。

日常移动和缩放不走这条事务；只改变几何。单会话与多会话共用主宿主；一变二、二变一不再触发 generation 抢编辑器、void 面板或延迟校准。

6.3 iframe 与手势

真实 iframe 面板不能因为换父节点重载。外层使用合适的常驻渲染策略，内层不更换 DOM 父节点；原生 provider 的可见性监听与尺寸测量仍需适配。renderer: 'always' 不意味着被移除的 Panel 永远不销毁，也不是完整的跨层无损证明。[S2]

拖动期间使用正确捕获事件的临时屏障保护 iframe 边界，结束／取消均释放。不能把一个 pointer-events: none 的透明层当成可拦截事件的盾。数据、编辑器和 iframe 的真实生命周期必须用集成测试验证，不能只看草稿字符串相同。

Electron 的系统拖窗区域与内容拖动区域明确分开。会话标题、Sidebar 标题和控件属于内容交互，不应拖动整个操作系统窗口。[S12]

07 · 保存、恢复与旧版本迁移

7.1 两层保存，不产生两份事实

原生 Sidebar 继续使用其逐 Session 存档和资源恢复方式。插件只新增“外层会话布局＋逐会话 Sidebar 停靠位置与比例”。不要修改原生 key 的含义，也不把导航、连接或 token 放进 Dockview params。[S9][S11]

建议存储键按连接／profile 命名空间隔离，例如 dsh.split.workbench.v1.<connectionScope>。身份由已认证的宿主解析，客户端 key 不是权限机制。初版仅本浏览器保存，不做云同步。

插件快照包括：schemaVersion、宿主基线、锁定的布局引擎版本、可恢复的 Panel 与 Session 引用、Dockview 布局、SidebarPlacement。限制体积、深度、重复 Session、未知类型和畸形数值。

7.2 恢复流程

先等待宿主身份和 provider 就绪 → 验证快照与版本 → 准备引用 → 校验唯一性 → 采用原生 Sidebar 已保存状态 → 一次恢复外层布局 → 报告真实可见范围。只有明确存在的 Session 与资源才可呈现。

会话已删除显示可处理的失效状态；权限失效不得显示敏感标题；provider 暂缺保留占位，不立即清空布局。存储失败仍能在内存里工作，并提示不能长期保存。

恢复不得自动发送消息、启动 Agent、新建终端或重启已退出进程。原生终端应恢复已保存身份，进程已失效时按原生提示处理。[S8]

7.3 旧 dsh.split.v1 的处理

只迁移能验证的、去重的会话引用。旧 overlay、generation、临时空格、主格特权、StagePool／GridDom 提案字段不进入新快照。旧列树若不能无歧义转换，以保留会话列表、重置几何的方式一次性提示；不搬运每个历史补丁字段。

新旧 key 分开，保留旧快照备份用于回滚。不能为恢复工作台而删除 dsh.sidebar-right.v1.<sessionId> 等原生资源存档。

7.4 窄屏与多页面

当浏览器小于当前布局可用尺寸，临时只显示明确选中的会话。扩回原尺寸恢复原布局，不覆盖桌面几何，不自动关闭后台会话。

初版不实时合并不同浏览器标签页的布局；每页保持自己的活动布局，恢复时读取最新有效快照。其限制应写在文档，不为少量用户预建布局协同系统。

08 · 性能与可靠性目标

不以“完全不用 React”或“所有内容永久挂载”作为性能方案。目标是：交互期间不做与动作无关的渲染、重挂和重复订阅。

路径 工作预算
拖动会话／Sidebar 每帧只更新预览；正常移动时不创建编辑器、不读取历史全文；松手一次几何提交
拖动分隔条 每帧最多一次几何更新，尺寸变化即时；避免测量－写入－再测量循环
流式输出 按 Session 增量更新；A 输出不应重绘 B 的整段历史或保存整个布局
保存 布局事件防抖，结束时提交；token 不触发布局存档；异常有内存兜底
隐藏重内容 依原生保活语义保留必要 DOM／资源，暂停纯视觉动画与不必要高频绘制
销毁 释放该视图的订阅、临时事件与计时器；不泄漏捕获指针或透明屏障

正式验收先以两会话＋两 Sidebar 为基准，再压测四会话和长历史。60Hz 跟手是交互目标，不是本次已经测得的所有设备性能结论。记录浏览器、视口、硬件、历史量、iframe、终端和模型输出负载后再公布结果。

最低验收包括 Chromium/Edge 的 Web、Windows Electron、macOS Electron；分别测试 100%／125%／150% 缩放、中文输入、系统标题栏、键盘焦点、拖过 iframe 和 reduced-motion。触摸命中区使用平台合适的尺寸，方向菜单作为拖拽替代；不额外引入一套移动端业务状态。

10 · 低保真 Demo：可以验证什么

Demo 文件：dsh-split-interactive-demo.html。单文件，内联样式与脚本，没有 CDN、远程字体、登录、模型调用或 Shell 执行。常规浏览器打开即可操作。使用体验清单逐项验证。

10.1 真正可操作的交互

本版 Demo 已实现：会话间无可见分割线但仍可调整尺寸；Sidebar 右上角无额外图标，带轻微静态阴影；同圆角的会话与 Sidebar；无会话描边；轻灰非聚焦遮罩；点击/键盘/iframe 聚焦；左侧逐会话菜单；直接右／下分屏；取消菜单不导航；重复目标定位；原有两层拖动、尺寸、Esc、放大、关闭、窄屏、草稿、附件和模拟资源等交互。

没有自动加入 Sidebar 标签拆出。用户本次要求对其可行性和兼容性进行评估，因此下面单独记录方案与建议，不在 Demo 放一个未经确认的“看似可用”入口。

10.2 不能由 Demo 证明的内容

Demo 不运行 DSH，也不加载 Dockview。为保证下载一个 HTML 就能离线使用，外层几何使用了一个小型参考实现，输入用原生 textarea。生产方案仍采用前文的 Dockview 与 DSH 原生绑定，不能把 Demo 的布局树、消息 Store 或终端模拟器当作生产架构迁移。

它能验证产品交互合同和相对手感，不能代表 Dockview 最终帧率、Lexical 输入行为、真实 PTY、DSH 三方 provider、协议、权限或 Electron 热卸载已通过。正式接入必须再跑 P0—P4。

Demo 的终端和回复依赖本页面计时；页面关闭或重载后会停止，不自动重启模拟进程。用户附件仅记录名称与大小，文件内容不上传；保存后恢复的名称不代表仍持有文件字节。不存在未标识的真实网络操作。

10.3 建议体验顺序

保留初始 A。在左侧会话 B 的 ⋯ 菜单选择“向右分屏”，B 直接出现在 A 右侧。分别点击 A/B 正文、输入框和 Sidebar，观察非当前会话的轻灰层交换，不出现厚边框，也不需要第二次点击。

再将 B 设为当前，从左侧 C 的 ⋯ 菜单选择“向下分屏”，C 出现在 B 下方。打开已经显示的 A 的菜单，可看到分屏被禁用，点击“定位此会话”只定位。Esc 关闭菜单不改变布局。

其后按原有体验清单测试标题拖动、Sidebar 四边停靠、尺寸、取消、iframe 输入、模拟终端收起与显式关闭、附件、新建、主题和恢复。体验清单和重置仅是原型辅助，不拟新增为生产功能。

12 · 决策、限制与交付结论

本方案收敛的是功能范围，不削减正确性。输入唯一性、会话目标、资源生命周期和恢复验证是“已有功能能正常工作”的最低条件，不属于额外平台功能。

最终生产方案只需要回答三个问题：完整会话放在哪里；Sidebar 在这个会话的哪一侧；原生能力如何在这个位置保持正确。分屏由左侧列表菜单发起，聚焦只改变极淡遮罩，不改变业务绑定。 不再增加第四套“组／面板市场／布局模板”的用户概念。

当前可以冻结产品交互与视觉层级，用 Demo 评审实际手感；真正的工程开工点是 P0 原生契约验证。未经原生测试，不承诺无损热插拔、任意会话数量或所有硬件上的性能最优。

13 · Sidebar 标签拆出：可选增强评估

本节将需求解释为：同一个 Session 内，将 Sidebar 的一个标签移动成第二块可见的辅助内容面板；不迁移到别的 Session，不创建新的会话，不复制标签。它有明确价值，但是否纳入下一阶段需单独确认；本轮 Demo 未实现该能力。

13.1 原生基础与新增部分

固定版本的右 Sidebar 已支持最多左右两格、跨格移动、float/dock，底层有 planDropTab、planPlaceTab 和空格整理。DockLayout 明确保留标签稳定的 DOM 容器，并在切标签、跨格移动和浮动时管理保活。它不是完全从零开始。[S11][S14]

但原生的“两格 Sidebar”不等于“两套独立 Sidebar 服务”。其公开导航仍以当前呈现会话为中心，不暴露完整几何快照，部分布局操作是内部实现；固定版持久化也限定单格或左右两格。把第二格进一步摆到正文下方、任意布局，会扩大当前“正文＋一块 Sidebar”的结构与适配范围。

路线新增改动（相对当前计划）判断
A. 原生 Sidebar 范围内分成两块内容，保留一个 Tab 域中低：优先使用现有两格语义，增强标签拖动落点、独立面板的轮廓与会话内宿主适配。推荐作为可选第二步。视图同看有用，不引入新的业务控制器。
B. 在会话的任意位置分别摆放两块 Sidebar，能独立挪动中高：内部从两块内容变为正文＋多个辅助组，需几何、空位回收、显隐、焦点、持久化以及多级拖拽仲裁。不能称作小样式修改。只有 A 不满足实际使用时再做。
C. 跨会话移动或复制、脱离应用的独立窗口高：涉及会话身份、资源访问、编辑器／终端重复持有、跨窗口通信与生命周期。本次不建议，不属于此插件最小范围。

以上是静态代码基础上的相对工程评估，不是已测工时，也不是兼容性已通过。不能从低保真 DOM 能移动，就推出原生 provider 全部无损。

13.2 有必要的场景

例如同时看报告与 SQL、浏览器预览与终端、参考文档与执行日志。其价值是减少反复切标签，而不是增加窗口数量。窄屏同时再分两块会牺牲正文宽度，因此只在尺寸足够时开放，不作为默认布局。

13.3 建议的最小交互

首版增强最多两块辅助内容窗格，限定在同一会话的辅助区内。至少有两个实际内容标签、且满足空间约束时，拖某个标签到辅助区边缘，出现第二块落点。松手后移动该标签，原位置删除成员、目标接收成员；不复制、不新开会话。目标已存在时移入该窗格。

拖回原标签条即合并；空出来的第二格自动收回。仅有一个实际标签时不为了“拆出”生成一个没有内容的空面板。保留原生单例页、guide 的合并与兜底规则。键盘菜单可提供与拖动同义的“移到另一窗格／移回”，不新造命名布局或模式。

严格区分三层手势：会话标题移动完整会话；Sidebar/窗格标题移动允许的辅助区域；Tab 抓手移动标签。一次 pointer stream 只能由一层消费；跨会话和应用外均拒绝落点。

13.4 兼容性检查

风险必须保持的约束
标签身份与资源使用同一个 Session、Tab id、content identity 与 occurrence，不把一次移动拆成 remove→close→open；采用原生原子移动意图，不能在中间态让标签从 Tab 域消失。
终端与浏览器移动不调用 close handler，不分配替代 PTY。终端 DOM、输入权和尺寸仍由原生 provider 管理；iframe 不通过换父节点重新加载。
焦点与快捷键移动后重新解析并验证原生 command target；过期的 occurrence/导航目标必须失效。菜单“关闭”只作用于明确目标，不能回退关应用。
持久化优先保留原生合法的一/两格布局与标签成员清单，不把任意三块或跨区域自定义树写进原生同名 key。超出形态时必须显式迁移版本与恢复流程。
第三方 provider按真实 provider 测试 keepMounted、visibility、尺寸观察、原生扩展 slot 和资源持有。纯展示文本与浏览器、终端、可编辑子代理不能一概承诺。
保护原生系统只增加几何呈现与受控移动接口；不 fork 两套 Sidebar registry/controller，也不另建并行 Tab store。

DSH rc.2 明确区分“折叠保留进程”与“关闭终端标签结束进程”，因此“关闭旧标签、在新面板重新打开同一路径”是错误实现。标签持有、keepMounted、终端恢复和关闭清理必须使用同一条原生路径。[S8][S11]

13.5 建议结论

可行、有特定使用价值，但不为本次视觉与入口修订自动扩容。先交付当前稳定的单 Sidebar 形态；下一步优先评估原生两格的有限拆分 A，而不是直接开发自由多面板 B。需要只保留原生两格就能解决的场景，不额外嵌套一个完整 Dockview 或创建第二套资源体系。

启用前至少验收：浏览器输入与计数不丢、终端进程和输入权不变、文件预览不重复打开、唯一 Tab/guide 正确处理、拖回合并无空格、跨会话拒绝、保存恢复仍符合原生 schema、第三方 View 和子代理编辑根无重复。
